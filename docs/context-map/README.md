# Карта контекстов
[Исходник диаграммы](context-map.mmd). Стрелка от потребителя к поставщику обозначает зависимость от его опубликованного контракта, а не совместное владение таблицами.

## Rental — управление арендой
Владеет Rental, DriverEligibility, Saga, шагами, таймерами, ключами пользовательских запросов. Проверяет владельца запроса и допуск, координирует запуск и компенсацию. Отдельный контекст нужен, потому что правила аренды и пользовательский процесс отличаются от учёта физических машин и денег. Только Rental решает, что аренда ACTIVE; он не меняет таблицы Fleet. Identity — внешний поставщик идентичности; проверка допуска остаётся локальным бизнес-правилом Rental.

## Fleet — распределение автопарка
Владеет Vehicle и Allocation: характеристики, эксплуатационная пригодность, исключительное закрепление машины, монотонный allocationEpoch. Отдельный сервис защищает дефицитный ресурс независимо от числа инициаторов аренды. Только он создаёт/освобождает выделения. Каталог может показывать устаревшую доступность; окончательное решение принимает транзакция ReserveVehicle. Самостоятельного TTL-освобождения нет: после зависания устройства это было бы опасно.

## Payment — денежные операции
Владеет Hold, PaymentOperation, ProviderReference и журналом результатов. Отдельный сервис изолирует финансовые правила, платёжные токены, сверку с провайдером и ограниченный доступ к данным. Rental знает holdId и статус, но не хранит карточные реквизиты. Payment адаптирует внешний протокол банка через антикоррупционный слой: внешний статус преобразуется во внутренние HELD, RELEASED, REJECTED, UNKNOWN.

## Access — доступ к автомобилю
Владеет AccessSession, DeviceOperation, внешними подтверждениями и закрытыми sessionId. Отдельный сервис нужен для связи с устройствами, проверки повторов, отзыва полномочий и поздних результатов. Fleet отвечает «кому выделена машина», Access — «какой доступ реально подтверждён». Это разные данные. У Access есть адаптер телематики, скрывающий её формат сообщений.

## Отношения
Rental — потребитель published language Fleet, Payment и Access. Поставщики публикуют стабильные команды/события, Rental переводит их в собственные переходы. Identity Provider поставляет идентичность клиенту и Rental. Payment и Access защищают модель от внешних API через ACL (антикоррупционный слой). Общей доменной библиотеки и общей базы нет. Каждый контекст может выпускать совместимые изменения отдельно.

## Предварительные сущности и ограничения
| Владелец | Сущности и ключи |
|---|---|
| Rental | rentalId PK; userId; vehicleId; state; version; allocationId; holdId; accessSessionId; startedAt; UNIQUE userId среди незавершённых; UNIQUE(userId, route, idempotencyKey) |
| Fleet | vehicleId PK; allocationId PK; rentalId UNIQUE; allocationEpoch; UNIQUE vehicleId среди незакрытых; tombstone отменённого rentalId |
| Payment | operationId PK; rentalId UNIQUE для холда; amountMinor; currency; providerRef; desiredState; actualState |
| Access | sessionId = rentalId; grantOperationId UNIQUE; allocationId; allocationEpoch; desiredState; actualState; terminalClosed; evidenceAt |
| Каждый сервис | outbox(messageId UNIQUE); inbox(messageId UNIQUE); operation registry(operationId UNIQUE) |

Закрытые записи и журнал не удаляются раньше срока возможного повтора. Учебная политика: история 90 дней, ключи HTTP 7 дней, команды старше 24 часов не исполняются автоматически. Неизвестные операции сохраняются до разрешения; повтор после срока хранения переводится в проверку, а не выполняется заново.
